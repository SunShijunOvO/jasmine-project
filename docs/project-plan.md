# 项目计划

最近更新：2026-09-20。本文记录范围与设计的依据；当前执行情况见 [项目进度](progress.md)。

## 1. 已确认的出发点与约束

- 产品：Internship Tracker，服务正在寻找实习或校招机会的学生，开发者是第一位真实用户。
- 第一版使用范围（2026-09-17 已确认）：仅开发者本人在开发电脑上使用，不提供其他设备通过网络访问；这不排除同一台电脑内的前后端 HTTP 通信，架构采用本机前端、后端与数据库分工，具体配置待实现。不要求第一版支持多用户使用或跨设备访问。
- 问题：公司、岗位、职位描述、投递状态、笔试、面试和备注等求职信息分散，管理容易混乱。具体痛点的频率和影响尚未访谈确认。
- 学习目标：亲手把一个想法变为可运行软件，理解每个阶段为什么存在，逐步获得独立开发能力。
- 时间：2026-09-15 至 2026-10-20；2026-09-21 至 2026-09-27 数学建模竞赛期间不安排项目任务，包括预习、补课或补偿性赶工。
- 总窗口含首尾为 36 天，扣除竞赛 7 天，剩余 29 个可安排日期。学习者确认非竞赛期平均每天可投入约 6 小时，2026-09-15 当天可投入 3 小时；可用时间不等于实际完成时间，其他日程和已有能力仍需随项目校准。
- 第一版不加入 AI、自动抓取招聘网站、复杂推荐算法。RAG、Agent、向量数据库、LangChain、MCP、本地模型、vLLM 等不进入初期任务。
- 教学规则由 [AGENTS.md](../AGENTS.md) 维护。优先保留理解和完整开发经历，功能规模随现实条件收缩。

## 2. 需求与 MVP：范围已确认

MVP 是能够解决一个核心问题、可以实际使用并检验价值的最小版本。它的范围需要由真实场景推导。

| 分析阶段 | 当前结论 | 有结论后保留的内容 |
|---|---|---|
| 问题分析 | 假设场景：实习求职者同时投递十几份简历时，通知信息、时间安排、求职进度等可能分散在电话、短信、求职软件、日历等各个角落。<br />目前需要使用电子表格或者纸笔等进行汇总，<br />容易漏掉关键信息，而且需要反复核对，也很难将各处的信息进行联系。<br />可能造成错过笔试面试或者时间安排冲突导致的问题。 | 一个具体经历、现有做法、困难及其影响；预期场景须标明是假设 |
| 用户需求 | 用户需要能够在一处看到自己所投的各个岗位的基本信息、联系人信息、所处阶段等。<br />如果有明确的下一步，那么用户需要知道下一步是什么阶段，例如笔试还是面试，以及具体的时间和地点；<br />如果长时间没有回复，用户需要根据等待情况决定是否继续追踪该岗位。<br />假设依据：不同岗位流程不同、进度不同，而且信息分散在各个地方，需要反复核对，可能遗漏关键事项。 | 用户想获得的结果及对应问题证据 |
| 使用场景 | 用户在当前的假设下，用户在希望集中检查所有岗位的时候开始使用；<br />希望看到各个岗位的进度、最近的安排以及是否有岗位长期等待的情况；<br />用户可以决定准备重点或者可以安排行程，并且决定是否停止追踪长期无回复的岗位算作完成。 | 在什么情况下开始、想做什么、怎样才算完成 |
| 功能需求 | F1：允许用户新建条目，记录一个刚刚投递的岗位信息。当前岗位条目的最小信息是当前行为（投递行为）进行的时间，投递的公司名称，投递的岗位名称，该岗位的当前进度。保存验证：用户完成添加后，即使刷新或者退出重进，仍然能够看到刚才填写的信息，并且所有的信息内容与刚才填写的一致。F1 的优先级及理由：它是集中检查所有岗位的前提，如果用户不先添加并保存岗位，系统里就没内容可查。<br />F2：更新已有岗位信息。允许用户对某一条已有岗位记录进行进展更新或主动纠错。进展更新时，可以修改当前进度，并补充或修改下一步的时间、地点和线上或线下方式；线上地点可记录使用的软件、会议号等，线下地点记录具体地址。主动纠错时，可以更正录错的公司名称、岗位名称、投递时间或其他已记录的信息。统一原则：用户选择修改的内容正确保存，未选择修改的内容保持原样，其他岗位记录不受影响。保存验证：分别检查一次进展更新和一次主动纠错，确认目标记录中应修改的信息与用户提交内容一致，未修改的信息及其他岗位记录保持不变；刷新或退出重进后，上述结果仍然成立。F2 的优先级理由：进展更新让记录持续反映求职流程，主动纠错避免错误信息长期影响集中检查与判断。 | 为支持场景需要什么行为、如何验收、优先级与理由 |
| MVP | 2026-09-17 已确认：仅本人本机使用，包含 F1 新增、F2 更新及纠错、F3 集中查看、F4 删除；停止追踪通过 F2 标记并保留记录。具体边界及验收见下文。 | 本版必做、明确延后、端到端验收场景及范围取舍 |

**F3：集中查看已保存岗位的最新信息。**（2026-09-17，学习者授权导师代拟，并确认内容符合预期；作为上表功能需求的续项。需求已确认，不代表应用已实现或经过真实试用验证。）

- 用户行为：用户能够在一处查看自己已保存的所有岗位及各岗位最后一次成功保存的信息，用于集中检查求职进展。
- 最小可见信息：每条岗位记录的公司名称、岗位名称、投递时间和当前进度；已有明确下一步安排时，还能看到下一步事项及已保存的时间、地点和线上或线下方式。未记录的安排应能与已确定的安排区分，不推测时间、地点或招聘方决定。投递时间支持用户判断从投递起已等待多久，不要求系统自动判断是否应停止追踪。
- 验收条件：预先保存一条仍在等待回复的岗位和一条已更新为待面试、已补充安排的岗位。进入集中查看时，两条记录均可找到，无遗漏或重复展示；各自的信息与最后一次成功保存的内容一致，没有串到其他岗位。待面试岗位显示更新后的进度与安排，等待回复岗位不出现未保存的安排；刷新或退出重进后仍能正确读取。尚未保存任何岗位时，应明确呈现没有记录的状态。
- 优先级理由：集中查看直接交付“在一处掌握各岗位进展”的核心价值；只有新增和更新而不能重新查看，用户仍无法利用已保存信息安排准备重点或判断等待情况。
- 范围：不规定列表、卡片或具体页面实现；筛选、排序、搜索、自动提醒和自动判断是否停止追踪不作为 F3 成立的前提。筛选和排序已于 2026-09-17 确认延后。

**F4：删除岗位记录。**（2026-09-17 用户已确认。）

- 用户可以删除误建或重复添加的记录，删除前明确确认目标；取消确认时保留记录。
- 验收：确认删除后，目标记录不再显示，刷新或退出重进后仍不存在，其他记录不受影响；第一版不提供回收站和恢复。
- 理由：修改信息无法消除多余记录，删除使集中查看保持准确。
- 已真实投递但决定停止追踪的岗位，通过 F2 标记为“停止追踪”并保留记录。

**核心端到端验收草案（导师整理，待实际实现时执行）：** 从空记录开始新增两个岗位；重新进入后核对信息；为其中一个更新面试安排并纠正岗位名称，确认另一条不变；集中查看最新结果；将一个岗位标记为停止追踪并确认仍保留；额外新增一条误建记录，确认删除后重进仍不存在，原有记录保留。当前仅有验收计划，没有运行验证结果。

当前不预设页面数量、数据字段、投递状态枚举、通知机制或账户体系。确认功能时，应能追溯到用户需要和使用场景；暂时说不清价值的想法先留待讨论。

2026-09-17 已确认延后：筛选、排序、搜索、联系人管理、独立 JD 与备注管理、自动提醒、账户、跨设备访问、回收站及删除恢复。下一步安排中必要的会议号、地址等仍保留；AI、抓取、复杂推荐、日历集成与冲突检测继续延后。前文用户需求保留较广的原始背景，第一版交付以此 MVP 边界为准。

后续进入最小数据、界面与系统分工设计；不继续扩展功能范围。

## 4. 数据、架构与目录：最小设计中

- 最小数据模型（2026-09-17，已确认）：第一版只设一种“投递记录”，每条表示一次岗位投递。包含系统生成且不随纠错变化的唯一编号、公司名称、岗位名称、投递日期、当前进度，以及可选的下一步事项、时间、方式和地点或会议信息。前四项业务信息必填，下一步信息未知时允许留空。
- 模型取舍（2026-09-17，已确认）：公司名称与岗位名称直接记录为文字；以唯一编号定位更新和删除，不以可修改的名称定位。每条只保存当前进度及最近一个下一步安排，不另建公司、用户、面试轮次或历史变更模型；停止追踪作为当前进度的一种取值。状态取值与时间精度等输入规则在实现相关操作前明确。
- 界面（2026-09-17，已确认）：先用一个主页面集中查看岗位，提供新增、编辑和删除入口；新增与编辑使用相同的信息组织方式，删除前显示目标并确认。
- 系统分工（2026-09-17，已确认）：采用 React 前端、FastAPI 后端与本机 PostgreSQL。浏览器前端负责展示、输入及操作反馈；本机后端负责检查输入、定位记录并执行读写；PostgreSQL 持久保存记录。各部分都在开发电脑上运行，不提供其他设备访问。
- 首条实现流程（2026-09-17，已确认）：从填写新增信息、前端请求后端、后端校验并写入数据库、保存成功后返回记录，到前端显示结果；刷新后重新读取仍存在。失败时保留输入并显示失败，不显示保存成功。
- 前端首次读取状态（2026-09-20，学习者已形成）：页面打开后请求 `GET /applications`，请求期间显示加载；成功有记录时逐条展示，成功空数组时显示没有记录，失败时显示读取失败，不能把失败伪装成空记录。最小状态包含岗位数据、加载标记和错误信息；已有数据上的重新刷新失败如何处理尚未设计。
- 首条流程的最小 API 草案（导师建议，作为实现起点）：前端通过 POST /applications 新增投递，输入公司、岗位、投递日期与当前进度，下一步信息可选；成功持久保存后返回 201 及包含唯一编号的完整记录。前端通过 GET /applications 读取全部投递，成功返回 200 及记录集合，没有记录时返回空集合。
- API 失败规则草案：新增输入缺失或无效时返回明确的校验错误且不保存；保存或读取失败时明确报错，不能假报保存成功，也不能把读取失败显示为没有记录。具体字段名、日期格式及错误结构在编写对应接口前确定。
- F1 输入规则（2026-09-17 已确认）：公司名称和岗位名称为必填文本，去除首尾空白后不得为空；投递日期为必填日期，必须能够解析为真实年月日；当前进度为必填的受限状态值。第一版状态细分为“已投递、待笔试、笔试后等待、待面试、面试后等待、已录用、已拒绝、停止追踪”。其中两个“结束后等待”状态用于表示当前环节已完成但尚无下一步通知，支持判断等待时间及是否停止追踪。当前程序枚举值采用学习者编写的 `applied`、`awaiting_written`、`finish_written`、`awaiting_interview`、`finish_interview`、`offered`、`rejected`、`stopped`；命名并非最终对外文案，但现阶段不继续打磨。下一步安排字段在实现 F2 时再补充规则。
- 认证、错误处理与日志：随访问范围和真实实现需要逐步确定；部署前明确适用的访问保护与数据处理要求，不提前承诺复杂账户系统。
- 目录建议：后端代码放在 backend，前端实现时再建立 frontend；目录是否创建待后续检查，不提前生成模块骨架。开发环境沿用学习者已有的 Conda，不再要求创建 .venv；环境目录不纳入 Git 或交付。
