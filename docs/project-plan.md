# 项目计划

最近更新：2026-09-15。本文记录范围与设计的依据；当前执行情况见 [项目进度](progress.md)。

## 1. 已确认的出发点与约束

- 产品：Internship Tracker，服务正在寻找实习或校招机会的学生，开发者是第一位真实用户。
- 问题：公司、岗位、职位描述、投递状态、笔试、面试和备注等求职信息分散，管理容易混乱。具体痛点的频率和影响尚未访谈确认。
- 学习目标：亲手把一个想法变为可运行软件，理解每个阶段为什么存在，逐步获得独立开发能力。
- 时间：2026-09-15 至 2026-10-20；2026-09-21 至 2026-09-27 数学建模竞赛期间不安排项目任务，包括预习、补课或补偿性赶工。
- 总窗口含首尾为 36 天，扣除竞赛 7 天，剩余 29 个可安排日期。学习者确认非竞赛期平均每天可投入约 8 小时，2026-09-15 当天可投入 3 小时；可用时间不等于实际完成时间，其他日程和已有能力仍需随项目校准。
- 第一版不加入 AI、自动抓取招聘网站、复杂推荐算法。RAG、Agent、向量数据库、LangChain、MCP、本地模型、vLLM 等不进入初期任务。
- 教学规则由 [AGENTS.md](../AGENTS.md) 维护。优先保留理解和完整开发经历，功能规模随现实条件收缩。

## 2. 需求与 MVP：逐步推导中

MVP 是能够解决一个核心问题、可以实际使用并检验价值的最小版本。它的范围需要由真实场景推导。

| 分析阶段 | 当前结论 | 有结论后保留的内容 |
|---|---|---|
| 问题分析 | 假设场景：实习求职者同时投递十几份简历时，通知信息、时间安排、求职进度等可能分散在电话、短信、求职软件、日历等各个角落。<br />目前需要使用电子表格或者纸笔等进行汇总，<br />容易漏掉关键信息，而且需要反复核对，也很难将各处的信息进行联系。<br />可能造成错过笔试面试或者时间安排冲突导致的问题。 | 一个具体经历、现有做法、困难及其影响；预期场景须标明是假设 |
| 用户需求 | 用户需要能够在一处看到自己所投的各个岗位的基本信息、联系人信息、所处阶段等。<br />如果有明确的下一步，那么用户需要知道下一步是什么阶段，例如笔试还是面试，以及具体的时间和地点；<br />如果长时间没有回复，用户需要根据等待情况决定是否继续追踪该岗位。<br />假设依据：不同岗位流程不同、进度不同，而且信息分散在各个地方，需要反复核对，可能遗漏关键事项。 | 用户想获得的结果及对应问题证据 |
| 使用场景 | 用户在当前的假设下，用户在希望集中检查所有岗位的时候开始使用；<br />希望看到各个岗位的进度、最近的安排以及是否有岗位长期等待的情况；<br />用户可以决定准备重点或者可以安排行程，并且决定是否停止追踪长期无回复的岗位算作完成。 | 在什么情况下开始、想做什么、怎样才算完成 |
| 功能需求 | F1：允许用户新建条目，记录一个刚刚投递的岗位信息；<br />当前岗位条目的最小信息是当前行为（投递行为）进行的时间，投递的公司名称，投递的岗位名称，该岗位的当前进度；<br />保存验证：用户完成添加后，即使刷新或者退出重进，仍然能够看到刚才填写的信息，并且所有的信息内容与刚才填写的一致；<br />F1 的优先级及理由：它是集中检查所有岗位的前提，如果用户不先添加并保存岗位，系统里就没内容可查。 | 为支持场景需要什么行为、如何验收、优先级与理由 |
| MVP | 待确定 | 本版必做、明确延后、端到端验收场景及范围取舍 |

当前不预设页面数量、数据字段、投递状态枚举、通知机制或账户体系。确认功能时，应能追溯到用户需要和使用场景；暂时说不清价值的想法先留待讨论。

后续按需要逐个澄清：其余必要功能行为与验收、第一版使用方式和访问范围、MVP 必做与延后边界。不要一次布置完整问卷。

## 3. 暂定技术栈及引入理由

以下清单来自学习者的初始计划。理由是待项目验证的候选理由，不代表已选定具体版本、已安装或已经掌握；没有技术替换决策。

| 技术 | 准备承担的职责与候选理由 | 引入时机 |
|---|---|---|
| TypeScript | 前端开发语言，用类型描述数据、帮助发现部分错误 | 开始前端实现时 |
| React | 组织交互界面与可复用界面部分 | 核心界面与交互需要实现时 |
| Vite | 支持前端本地开发和构建 | 开始搭建前端运行环境时 |
| Python + FastAPI | 实现服务端规则与供前端调用的接口 | 核心流程需要后端服务时 |
| PostgreSQL | 持久保存具有结构和关系的数据 | 核心场景要求保存并再次读取数据时 |
| SQLAlchemy | 在 Python 中组织数据库访问和对象与数据的映射 | 理解基本数据模型并接入数据库时 |
| Git + GitHub | 保存变更历史，并支持仓库托管和展示 | 从值得保留的文档阶段开始学习 Git；托管操作由学习者完成 |
| Linux | 项目当前开发环境，也是计划中的部署环境 | 从日常文件与进程操作按需学习 |
| Docker / Docker Compose | 描述运行环境，组织需要一起运行的服务 | 已理解应用怎样运行，出现环境复现与部署需要时 |
| AI | 是否采用及用途均待判断 | 基础产品完成、实际使用暴露适合的问题之后 |

引入每项技术时，再讨论职责、必要性、常见替代与取舍。若某选择明显增加负担却无当前收益，先解释并讨论，再记录是否调整。

## 4. 数据、架构与目录：尚未设计

- 数据模型：待核心场景确认后，讨论需要记住什么、数据之间有什么关系和约束。
- 界面与前后端分工：待需求确认后，围绕一个核心操作设计。
- API：待确定调用方、输入、输出、失败情况和负责的业务行为。
- 认证、错误处理与日志：随访问范围和真实实现需要逐步确定；部署前明确适用的访问保护与数据处理要求，不提前承诺复杂账户系统。
- 源代码目录与模块：尚未规划，不预先生成目录骨架。
- 测试、容器、部署方案：待运行方式和核心验收场景明确后补充。

### 节奏检查与缩减规则

- 09-20：根据实际进展留下竞赛前交接；未完成的分析如实保留，恢复后接续，不跳过。
- 09-28：读取交接，确认当日可用时间和理解情况，重排剩余窗口。
- 每个里程碑结束，或同一任务连续两次工作仍无进展时：定位是范围过大、知识缺口还是环境阻塞，拆小任务并调整后续计划。
- 10-09 若核心流程尚未贯通：立即复核并收缩 MVP，不继续扩展功能面。
- 调整优先延后次要场景、视觉精修及扩展能力；保留核心流程、必要数据保护、基本测试、一次部署和真实试用。技术无法按期引入时先说明取舍，再讨论方案。
- 10-20 的目标是完成一次有证据的完整流程；不承诺在一个月内熟练掌握所有技术。若缩减后仍不可行，如实重估交付内容，不由导师接管实现来掩盖进度。
